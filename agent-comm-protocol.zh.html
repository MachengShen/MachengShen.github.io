Agent 间通信协议：按 Privacy Policy 决定共享什么

一句话。两个人各自有 AI agent 时，可以用一套开放协议让 agent 之间通信；每一方用自己写的 Privacy Policy / 本地策略，决定哪些技术经验、insight 愿意交给对方的 agent——相当于受策略门控的 specialized knowledge sharing，而不是把聊天记录或账户数据整包甩出去。
诚实边界。这是公开协议草稿 + 规范与参考实现入口，不是托管聊天服务，也不是「替代微信」。传输仍可走邮件、webhook、Matrix 等已有通道；本层管身份、信任档、策略、回执。实验性（v0）。私聊原文、微信群名、内部主机与密钥不出现在本页。

这是什么 / 不是什么

  • 是 用户自有的薄协议层：收件箱、寻址、信任档、策略、回执。
  • 是 agent↔agent 身份认证、委托权限与安全消息的公开规范（SPEC-0003）。
  • 是 「你定策略 → agent 按策略决定分享边界」——平台不再替你决定什么到达、什么外泄。
  • 不是 新聊天 App / 新超级平台。
  • 不是 要求每条私信都给 AI 读。
  • 不是 发明新密码学；安全组合已有标准（见 SPEC-0003）。

和群里那句话怎么对齐

若你对别人说的是：

  • 「我们的 AI 用一套专门给 agent 通信的 Protocol」→ 对应本页 + 下方 SPEC；
  • 「Agent 基于你制定的 Privacy Policy 决定哪些 technical 东西愿意共享」→ 对应 SPEC-0001 的 Trust tiers + AgentPolicy（本地策略门控）；
  • 「你造系统卡住时，我这边 agent 可以给 advice；你那边 Web3 insight 反过来帮助我」→ 目标用法：在策略允许的范围内做 expertise 交换，而不是互挖私密记忆。

最薄的有用回路

message → local identity → local policy → receipt → audit

  1. 身份 / 地址：谁、经哪条通道。
  2. 信任档（接收方本地）：direct / priority / standard / public / blocked——不是全球关系真理。
  3. AgentPolicy：按档决定投递、摘要、委派、仅审计、或拦下。
  4. Receipt：生命周期状态，而不只是「送达」。
  5. Audit：每次路由决策可本地审计。

欢迎什么反馈

  • 策略模型哪里不够用（例如「只分享某类 technical advice、绝不分享联系人」）
  • 接入摩擦：邮件 / webhook / 其它通道适配
  • 权威委托与吊销：人怎么清晰授权、怎么一键停
  • 误拦 / 误放：false-negative / false-positive 监测（见 SPEC-0002）
